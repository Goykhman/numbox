numbox.core.configurations

Overview

Every function numbox caches is decorated under one set of numba options, jit_options, read once from the NUMBOX_JIT_OPTIONS environment variable when this module is first imported; a bare @njit in numbox, as in lowlevel.py, meminfo.py and make_vector, is not cached and takes none. The value is a JSON object passed to @njit as keyword arguments, and any other shape is refused by name, as is a cache that is not true or false (the string "false" is true to numba, which reads the option’s truth); unset means {"cache": true}, so numbox compiles into numba’s on-disk cache by default, and export NUMBOX_JIT_OPTIONS='{"cache": false}' turns that off.

Where the cache lands

numba writes a cached function’s entries under NUMBA_CACHE_DIR when that is set, else into the __pycache__ directory beside the function’s source file, else into the user’s cache directory, taking the first of those it can write. It sets the cache up when the function is decorated, so with caching on the question of where it lands is settled at import. The user’s cache directory is ~/Library/Caches/numba on macOS, %LOCALAPPDATA%\numba\Cache on Windows, and $XDG_CACHE_HOME/numba elsewhere, ~/.cache/numba when XDG_CACHE_HOME is unset.

Where no cache can be written, numba raises at decoration, and numbox’s import used to die on its first module with RuntimeError: cannot cache function ...: no locator available for file .... The two placements that do that are a read-only install whose user cache directory cannot be written either, and an import from an .egg, .whl or .pyz archive, which Spark’s --py-files ships. Since every function numbox caches decorates under the one jit_options, numbox puts the question once, when this module is imported, and answers it for the package: for a probe in each directory of the package that holds a module, since numba’s in-tree cache is a __pycache__ beside each source, it runs the cache set-up numba runs at decoration and the writability check numba runs at the first save, compiling nothing, and where either fails for any directory numbox compiles without a cache and one RuntimeWarning names the remedy. Every directory counts, whether or not its modules cache anything, so the answer errs toward uncached, which is never wrong. A module that survives as .pyc alone is asked by the file it was compiled from, which its code keeps and numba looks up: the .py that is gone where it was compiled in place, or a tree elsewhere, on disk or not. For a .zip, which numba caches per directory of the archive, each in a location of its own under the user’s cache directory, the archive’s directories are listed and the question put for one module of each; a .pyc in the archive that zipimport would run, which it takes before the .py beside it unless it is stale against it or of another interpreter, and whose code keeps the file it was compiled from, is asked by that file, since that is what numba looks up for it, on disk or gone, and one zipimport would pass over is passed over, and a .pyc whose code names a member the archive does not hold, one alone with no .py beside it or one compiled to name another path in the archive, compileall -d, beside its .py or not, is asked for itself whichever member stands for its directory, since numba 0.68 and later read the member’s source from the archive by the name its code gives and find none for it; any other archive has no location at all. A function numba cannot cache is compiled in every process that uses it, never wrong; that is the cost the warning reports. An error at decoration that is not the cache’s is raised as it was.

A package built on numbox can put the same question for its own files: check_cache_location asks it for one file, is_a_cache_error tells numba’s cache errors from the rest, and cache_remedy words the remedy, given the package’s name for the two remedies that tell the reader to install it again, at a shorter path or with its source files on disk. The bound on file names is the package’s own: LONGEST_CACHE_FILE_NAME holds numbox’s functions only, so a package passes check_cache_location the longest name numba writes for its own, as longest_file_name, or a location that fits numbox’s names and not the package’s passes the check and the first save overflows it.

The code numbox generates at run time, make_structref’s, compile_kernel’s, the work builder’s derives and the sqlite registrations’, is anchored to a file under NUMBA_CACHE_DIR or the user’s cache directory so that numba can cache it. That directory can be unwritable where the package’s own functions cache, since those cache beside their sources, so each anchor puts the same question for its own file when it is written, and the code it names compiles without a cache where the answer is no, after a warning of the same shape (the builder’s derive falls back without one, as it did). make_structref, compile_kernel and the builder take jit options of the caller’s, which the variable does not reach, and compile_kernel’s cache argument overrides those too, so that warning’s silence is cache off in the options the code was given, the argument where it takes one, or the variable where the options are the package’s. make_graph’s kernel is anchored to the builder’s own file and cached beside it, so it puts the question for that file under the options it was given, and falls back the same way with the package’s remedy for the placement. See the cache-anchor section of numbox.utils.

Modules

numbox.core.configurations

numbox.core.configurations.cache_remedy(py_file, failure, silence, package='numbox')[source]

The remedy for failure, numba’s error for a function whose file is py_file, ending in silence.

The remedy is one sentence. It names what numba tried, why that failed and what moves it, and ends in silence, the clause that says how to turn caching off. py_file can be a string, bytes or a path object, and so can the file name the error carries; both are read as strings. package is the package the remedy tells the reader to install again, at a shorter path or with its source files on disk. A package built on numbox that asks the question for its own files, with check_cache_location and is_a_cache_error, passes its own name, just as it passes check_cache_location a longest_file_name for its own functions; LONGEST_CACHE_FILE_NAME is numbox’s.

Most of the remedy turns on which locator took the file. numba caches a source file on disk in one of three places: a directory under NUMBA_CACHE_DIR if that is set, else the __pycache__ beside the source, else a directory under the user’s cache directory. The first and the third are under a cache directory named after the source’s directory, by its name and a hash of its path. The three can nest, and NUMBA_CACHE_DIR set to the user’s cache directory makes one path of two. So the remedy matches the whole path the error names against the location each locator numba reaches would give the file, in the order numba tries the locators, and reads the error as the first matching locator’s. numba’s own errors mean that the locators before that one passed the file over; an error a caller passes on, naming a location numba did not take, need not mean that. numba reaches no locator listed after its .zip locator for a path with .zip in it, because that locator takes the file without trying its location, so a location that one of those would give is none of numba’s.

NUMBA_CACHE_LOCATOR_CLASSES decides the order. Each entry is one of three things: a class of numba’s caching module; a subclass of such a class, by its dotted path, which takes what its parent takes, caches where its parent does, and is told as its parent is; or a class outside numba’s families, with a from_function and a place of its own, which takes whatever its from_function takes when asked with a probe, as numba asks it, and caches in a place that only the class can name. An error naming a location that no locator of numba’s gives the file is told that location as the error names it; the location is then that class’s. An error naming no file is told the location numba took as the outside class’s own, with no path to name, among the places of numba’s locators that are reached. numba’s IPython locator takes a file on disk only in an ipykernel directory, and its .zip locator only a path with .zip in it, so listing either ahead of the rest changes nothing for any other file. The .zip locator listed first takes such a path before any other locator does. It caches the file under the user’s cache directory if a part of the path ends in .zip, an archive or a directory; if no part does, it finds no archive and raises, and the remedy asks for a locator for a file on disk listed before it. The user-provided locator counts only with NUMBA_CACHE_DIR set, because it takes nothing without. Listed after some of the locators for a file on disk, the .zip locator finds no archive and raises once those have passed the file over, and numba tries none after it; the remedy then asks for one of their locations to be made writable, or for such a locator to be listed before it. A list with no locator that takes the file is told so, and so is a list whose only locator for the file is the user-provided one with NUMBA_CACHE_DIR unset, which is told to set the variable. Both are told the same for an error a caller passes on under such a list, as for numba’s no-locator error, because numba took no location under it.

For a source file on disk, NUMBA_CACHE_DIR is offered, because that is the only kind of source numba reads the variable for. If the variable is set and numba passed it over, the remedy names it and asks for a writable directory at a short path. numba passes over a directory too deep to make its own directory in, as it does an unwritable one. If NUMBA_CACHE_LOCATOR_CLASSES leaves the user-provided locator out, numba never reads the variable, and the remedy asks for the locations the list names to be made writable. If the location numba took refuses a file for another reason, a full disk or permissions changed since numba’s own check, the remedy names the location and the reason and asks for room or a writable directory there. It offers NUMBA_CACHE_DIR as the alternative if numba tries the variable before that location’s locator, or the variable set to another directory if the location is the variable’s own. numba passes over a location it cannot make or write in, so only its no-locator error means the variable was passed over. A location that is none of numba’s is named as the error names it. If numba tries NUMBA_CACHE_DIR before any other locator, the variable is named as set, to be made a writable directory at a short path, or, unset, asked for at a short path for a path too long and as a writable directory otherwise; nothing is said of numba passing it over, because such a location cannot show that.

For a path too long for the file system, the error names the location, and the remedy fits the one it is: a shorter NUMBA_CACHE_DIR for the first of the three; the package at a shorter path for the second; the user’s cache directory at a shorter path for the third, through XDG_CACHE_HOME or HOME, HOME alone on macOS and nothing on Windows. For either of the last two the remedy also offers NUMBA_CACHE_DIR set to a short path. It makes that offer if numba tries the variable before the locator that took the location, or before the last of the locators that give the file that one path, as the user-wide and .zip locators do. If the variable is set and numba passed it over, the remedy names the variable and asks for it to be made a writable directory at a short path.

A name can be too long for the file system. The directory numba names after the source’s directory, under NUMBA_CACHE_DIR or the user’s cache directory, is that directory’s name plus forty-one bytes. A name longer than the file system holding the location allows can be made at no path, and is refused whatever the errno, EINVAL on Windows. The limit is asked of the system, 255 if it cannot say, in bytes, or in the UTF-16 units Windows and macOS count a name in. Three errors are told the name and its length, and to put the file in a directory of a shorter name. The first is an error naming such a location. The second is numba’s no-locator error for a file on disk, or its .zip locator’s error once the locators before it passed the file over, if every locator numba tried that names its cache directory by that hash found the name too long; the variable’s locator measures by the limit of the directory the variable is set to, or by 255 if it is unset, and under that locator alone, unset, the remedy also asks for the variable to be set. The third is a frozen application’s error. For a file on disk the remedy adds the __pycache__ beside the source, which caches under no such name: made writable if numba reaches the in-tree locator; otherwise, under a list, that locator listed, before the .zip locator or the outside class that took the file if the list puts it after one.

The files numba writes for a function are named after the source’s name and the function’s qualified name. A cache file numba could not make or open in the location it took, because its name is longer than that file system allows, is told the name and its length, which no shorter path cures. It is told a shorter name for the function or its file, which is the package’s to give. If a file system in use takes the name, the remedy also offers NUMBA_CACHE_DIR pointed at a directory on such a file system: the variable as set, if its own location took the file, and otherwise provided numba tries the variable before the locator that took the file, as the variable is offered at a short path for a path too long. A file system in use takes the name if the name’s base fits in 255, the common limit, less the 29 bytes numba adds for the longest name it writes for the function: a data file’s, with three digits for its number, which numba counts from one without bound, written through a temporary name; a wider number in the error’s name counts at its own width. The check’s error for a name as long as the package’s functions get, on a file system that takes no name that long, is told the length. It is offered NUMBA_CACHE_DIR pointed at a directory on a file system that takes such a name, on the same terms, whatever the name’s length. Nothing is offered for a .zip member, which the variable does nothing for.

A path can hold bytes that are not UTF-8. numba hashes the source’s directory path as UTF-8 for the name of its directory, and raises at decoration for such bytes when a locator that names its cache directory by that hash reaches the file. For such a path the remedy names no location under NUMBA_CACHE_DIR or the user’s cache directory. A .zip under such a path, whose archive path numba’s .zip locator hashes the same way for its directory under the user’s cache directory, is told to put the archive under a UTF-8 path; a frozen application under one, whose path the user-wide locator hashes the same way, is told to put the application under a UTF-8 path. A file on disk under such a path is also told the __pycache__ beside it, because the in-tree locator hashes no path for that directory. If the list leaves the in-tree locator out, or puts it after a locator that hashes other than the variable’s, the remedy says to list the in-tree locator before the first locator that hashes. If only the variable’s locator hashes before the in-tree locator, the remedy says to unset NUMBA_CACHE_DIR. If the in-tree locator came before every locator that hashes and passed the directory over, the remedy says to make the __pycache__ writable. With any of these, the remedy also says to make the __pycache__ writable if it cannot be written.

numba’s IPython locator caches a cell file in numba_cache under IPython’s cache directory, with no directory per file, and passes the location over if it cannot make or write in it. No other locator of numba’s takes a cell, so a cell then gets numba’s no-locator error. It is told that location, to be made writable or put at a shorter path, or IPython’s cache directory to be given a home if IPython raised for it; a class outside numba’s families listed with the locator is named as having passed the cell over too. That location too long is told as IPython’s cache directory at a shorter path, for a cell file on disk and for a .zip member in an ipykernel directory alike, if the IPython locator is listed before the .zip one; no NUMBA_CACHE_DIR is offered for a source not on disk. IPython is asked for its directory only if a locator of that family is listed and takes the file, never for any other file, a plain .zip member among them. The reason is that IPython warns when asked under a home it cannot write, and leaves a temporary directory behind. numba imports IPython when it makes the location and catches only OSError there. So if IPython is not importable, numba raises ImportError at decoration for a file that the IPython locator takes, which is no cache error. An error a caller passes on naming that location is told as none of numba’s if another locator numba reaches has a place for the file; if none has, the list is told, as for numba’s no-locator error. If IPython raises OSError for its directory, numba passes the locator over, as it does a location it cannot make, and the remedy, which asks the same question, has no location of IPython’s to match the error against.

A file in an ipykernel directory that numba’s IPython locator takes, a cell file on disk or a .zip member, can meet an IPython that gives a new temporary directory as its cache directory on every call. IPython does that if it can write neither that directory nor its own. An error naming a file is then told so, with IPYTHONDIR or XDG_CACHE_HOME at a writable path as the remedy; the error numba’s first save raises there is FileNotFoundError, naming a file in the numba_cache directory it could not save in, because numba makes numba_cache in one such directory and saves in another. An error of another errno naming a numba_cache is a caller’s, and is told as the location it names. An error naming no file is told the locations numba could have taken, with its reason.

An error can name no file, carry an empty string or empty bytes as its name, or carry a name of another kind, an integer file descriptor, which counts as none. A caller can build such an error, and numba’s first save raises one when a write fails, as on a full disk. So does inspect when, for numba’s IPython locator, it reads no source in a cell file on disk, one that cannot be read or, before Python 3.13, an empty one; that error has no errno either, because no call into the file system raised it. For a file on disk that a locator of IPython’s family takes, numba having reached it, that error is told as inspect’s, the locator having tried no location: make the file readable, with the source in it. For a cell, whose source numba reads from linecache while IPython holds it to run the cell, the remedy says that numba caches a cell only while IPython holds its source. For a .zip member whose archive holds no source, a .pyc alone, the remedy is the archive’s: ship its source files. Every other OSError that check_cache_location raises names a file. An error with no name, or an empty one, is told the locations numba could have taken, in numba’s order and each once: for a path too long, to put whichever of them is too long at a shorter path; for a file refused for another reason, such as a full disk, the reason, and room or a writable directory there. A path object is never empty, because pathlib reads an empty string as the working directory, ., which the remedy names as a location that is none of numba’s.

numba caches a .zip and a frozen application under the user’s cache directory, and the remedy for either is that location made writable or given room, with the reason the error gives, a full disk or permissions. The .zip’s error names the location, a directory of numba’s under the user’s cache directory, or a file numba writes in it, as the first save’s error does, and the directory is told. An error naming a location that is none of numba’s, under the list and in its order, is told that location as the error names it, as for a source on disk. Nothing is said of what moves the user’s cache directory, or of where numba caches the file, which that location is none of. The frozen application’s error is numba’s no-locator one, which gives no reason, because numba passed the location over on its own error, unwritable or too deep alike; so the user’s cache directory is named as one numba could not use, to be made writable or put at a shorter path. If the name numba gives the directory after the source’s directory is too long for the file system, that is told instead; so is a cache file’s name too long for the file system, in that location or in IPython’s numba_cache for a member in an ipykernel directory, which no shorter path cures. A .zip’s location too long for the file system is the user’s cache directory’s doing, because the names numba makes are bounded, and the remedy is that directory at a shorter path, through what moves it on the platform. A frozen application’s path with .zip in it and no part ending in .zip gets the .zip locator’s error instead, if the list puts that locator before the user-wide one, or once the user-wide one passed its location over; the remedy is the user-wide locator listed before the .zip one, or the user-wide location made writable or put at a shorter path. An error that names no file, a caller’s or the first save’s on a full disk, is told the locations numba could have taken, as for a source on disk, in order and each once. It is told the reason, or, for a path too long, to put whichever is too long at a shorter path. For such an error, for a member in an ipykernel directory where a locator of IPython’s family is reached, the user’s cache directory is not named as where numba caches the file. IPython’s numba_cache is among the possible locations whenever IPython gives its directory.

numba caches a .zip through its .zip locator alone, so a list that leaves that locator out gives numba no locator for a source in a .zip, and the remedy is to list it. That holds for a member of an archive that exists; a directory named .zip above a source that is nowhere is no archive. The same holds for a notebook cell and numba’s IPython locator, and for a frozen application and numba’s user-wide locator, which alone takes one. Either is told for an error a caller passes on under such a list, as for numba’s no-locator error, because numba took no location. For any other kind of archive, or a module without its source, the remedy is the source files on disk or a .zip holding them, each with the locator it needs listed if NUMBA_CACHE_LOCATOR_CLASSES leaves it out. The source files on disk need one of the three locators for a file on disk, and NUMBA_CACHE_DIR set if the user-provided locator is the one listed; the .zip needs the .zip locator. A source that is neither in a .zip nor a frozen application’s, which no locator takes, is told the same for any error.

From numba 0.68 the archive’s stamp hashes the member’s source, which numba reads from the archive by the name the module’s code gives under the archive’s path. zipfile raises KeyError for a name the archive does not hold. For a module shipped as .pyc alone the remedy names the member and asks for the source files, on disk or in a .zip; for a .pyc compiled to name another path in the archive (compileall -d), whose source the archive holds beside it, the remedy is to compile the .pyc to name its own path, or to leave it out. On Windows under numba 0.68.0 every member gets that error, because that release builds the name with the platform’s separator (numba issue 10889, fixed for 0.68.1). If the archive holds the member’s source under that name with forward slashes, the name a release with the fix reads, the remedy is the install on disk, or a numba release carrying the fix; otherwise it is the remedy for any other member. numba takes the first part of the path ending in .zip for the archive, a directory so named above the file included, and from 0.68 opens it to read the source. The IsADirectoryError that gives is told the directory: put the archive under a path with no such directory above it. A file on disk under such a directory, which the .zip locator takes once the locators before it passed the file over, is told to make one of their locations writable, or, with the .zip locator listed first, to list a locator for a file on disk before it; or to put the file elsewhere.

numbox.core.configurations.check_cache_location(py_file, longest_file_name=0)[source]

Raise the error numba would raise if a function whose source file is py_file cannot be cached; else return.

py_file can be a string, bytes or a path object; it is read as a string.

The question is put to numba the way decoration puts it, in three steps. First the cache set-up, which picks the location for the file, or raises RuntimeError if no locator takes it. Then the source’s stamp, which decoration reads too: for a .zip it stats the archive, and from numba 0.68 it also reads the member’s source from the archive, as from 0.68 it reads a source on disk for its hash. Then the writability check, which decoration runs for every location but a .zip’s and the first save runs for all; it raises OSError.

The probe is compiled with py_file as its file. That is all a locator reads of it, except numba’s IPython locator, which also reads the function’s source, the way inspect reads it. inspect reads a file on disk from the file itself, a cell from linecache, where IPython holds the cell while it runs, and a .zip member through the loader of the function’s module; for a real module that loader is zipimport’s, which gives the member’s source from the archive. So the probe is a function of a module of its own, whose loader reads the member as zipimport’s does, and that module is in sys.modules while numba picks the locator. After the read, the lines linecache holds for the file are the member’s own, as any reader would leave them. For a member whose archive holds no source, linecache keeps the probe’s loader to ask again later; the check removes that linecache entry, so that no loader of the probe outlives the check. A cell linecache does not hold, or a member compiled to .pyc alone, raises inspect’s error, as it does for numba at decoration.

Nothing is compiled. Nothing is written but the cache directory itself, with one exception: an IPython that can write neither its cache directory nor its own makes a temporary directory on every call, and the check causes three such calls, two inside numba’s making of the directory and one of its own.

An OSError from the check names the location numba picked, with three exceptions. inspect’s error names no file. For a cell file on disk that numba’s IPython locator takes, inspect reads the source from the file itself before the locator tries its location, and raises if it finds no source there: a file it cannot read or, before Python 3.13, an empty one, which linecache then holds as a blank line. The stamp’s error names the archive that a .zip member’s code names, if that archive has since moved or cannot be read; the stamp is read once the locator is picked, as numba reads it at decoration. From numba 0.68, where the stamp hashes the source, the stamp’s error can also name the source itself, if it cannot be read. It can also name a directory named .zip above a file on disk, which numba’s .zip locator takes for the archive and opens.

A location can be absent once made. numba’s IPython locator asks IPython for its directory at every save, and an IPython that can write neither its cache directory nor its own gives a new temporary directory on every call. So the directory numba made is not the one it is told next. The check then raises FileNotFoundError naming numba_cache under the last directory IPython gave it, which numba never made. numba’s first save would instead name a file in numba_cache under the directory IPython gave numba when it set the cache up, a different temporary directory.

numba’s writability check makes a temporary file with a short name, or no file at all on Linux, while the files it saves have names of up to a hundred bytes and more. So a location within that length of the path limit passes numba’s check, and the first save dies. Given longest_file_name, the check also makes and removes a file with a name that long in the location, and the OSError it raises names the location. The package asks with LONGEST_CACHE_FILE_NAME, the bound on the names numba gives the package’s own files. If the name is longer than the file system holding the location allows, no shorter path cures that, so the error carries the length as longest_file_name and the remedy asks for a file system that takes the name.

numbox.core.configurations.is_a_cache_error(error)[source]

Whether error is numba’s error for a cache it cannot set up.

That is one of: no locator takes the file, a location numba cannot use, or, from numba 0.68, a .zip member whose source numba cannot read from the archive.

numba itself passes over a location on any OSError from making its directory or writing a file there: permission denied, a read-only file system, a path through a file, a component too long, a full disk. So any OSError counts. So does the ValueError numba raises for an archive under a directory whose name holds .zip: its .zip locator takes the file for that substring and then finds no .zip in the path. So does the KeyError numba 0.68 and later raise when they read a .zip member’s source from the archive, which they hash into the archive’s stamp. It is zipfile’s error, naming the member, for a name the archive does not hold. The name is missing for a module shipped as .pyc alone, and on Windows under numba 0.68.0 for any member, because that release builds the name with the platform’s separator (numba issue 10889, fixed in 0.68.1). And so does the UnicodeEncodeError numba raises when it hashes the source’s directory path as UTF-8 for the name of its directory under NUMBA_CACHE_DIR or the user’s cache directory. numba raises it for a path that holds bytes which are not UTF-8, decoded with surrogates. A locator that names its cache directory by that hash raises it at decoration when numba reaches it, the locators before it having passed the file over, so no location takes the file. Without this clause, a package installed under such a directory, with its __pycache__ unwritable, would die at import, while with caching off it imports.

numbox.core.configurations.uncached_where_no_cache_can_be_written(options)[source]

options as given, or with cache off, after one warning, if numba can write no cache for numbox.

numba sets a cached function up when the function is decorated, and raises RuntimeError there if no cache location can be written: in a read-only install whose user cache directory cannot be written either, or on an import from an .egg, .whl or .pyz archive, which Spark’s --py-files ships. For a .zip numba takes the user’s cache directory without checking at decoration that it can be written, and the first write raises OSError instead. Either way the import would die at the first decorated function, with nothing to name the way out.

Every function numbox caches is decorated under the one jit_options, so the question is put here, once, for a source file in each directory of the package that holds a module, and answered for the whole package. If numba can cache no function of one of those files, the options come back with cache off, and one warning names the remedy, as cache_remedy sets it out. For a source file on disk the remedy is NUMBA_CACHE_DIR, and, if the location is too long for the file system, whatever shortens the location numba took. For a .zip it is the location numba took under the user’s cache directory, made writable or given room, with the reason; or that directory at a shorter path, if the path is too long; or the .zip locator listed, if NUMBA_CACHE_LOCATOR_CLASSES leaves it out. numba reads NUMBA_CACHE_DIR only for a source file on disk. For any other kind of archive, a .pyc-only install or a .pyc in a .zip, the remedy is the source files on disk, or a .zip holding them, which numba caches in the user’s cache directory. The same goes, from numba 0.68, for a .zip member whose archive holds no source for it, a .pyc alone, because numba then reads the member’s source from the archive for the stamp; the member is named. On Windows under numba 0.68.0 every member is such a member, because the name is built with the platform’s separator (numba issue 10889), and the remedy is the install on disk, or a numba release carrying the fix. NUMBOX_JIT_OPTIONS='{"cache": false}' turns caching off and silences the warning. An error that is not the cache’s, as is_a_cache_error draws the line, is raised as it was.

A .zip whose cache directory holds every entry but can no longer be written takes the fallback too, where numba alone would have loaded the entries. The writability check is the rule numba applies to every other placement, and the one its .zip locator is missing, reported as https://github.com/numba/numba/issues/10888.

Options without a cache key, which NUMBOX_JIT_OPTIONS can give, leave njit to its default, which is off. But the sqlite virtual-table and table-valued-function callbacks cache under those options, so they are asked about too, and come back with cache off, explicitly, if the answer is no.
